01왜 이 문제인가

기술이 아니라 빈칸에서 출발했다.

화상회의에서 조명은 이미 여러 제품이 건드린다. 그런데 전부 프리셋이다. macOS Studio Light은 얼굴을 밝히고 배경을 어둡게 하는 한 가지 효과이고, NVIDIA Broadcast의 Virtual Key Light도 위치를 옮길 수 없다. 고품질 쪽인 SwitchLight는 포스트프로덕션 속도이고, 디퓨전 기반 실시간 연구인 LiveLight(TOG 2026)도 15.78 fps · 0.253 s 지연이다.

비어 있는 칸은 실시간 + 위치 제어 + 손 인터랙션 + 맥 네이티브다. 그리고 이 조합에서는 지연이 곧 품질이다 — 손으로 무언가를 잡는 경험에서 250 ms는 "반응이 느리다"가 아니라 "잡히지 않는다"로 느껴진다. 그래서 처음부터 물리 기반 렌더링을 택했다. 품질 상한은 디퓨전이 높지만, 이 제품이 파는 것은 화질이 아니라 손끝에 붙는 느낌이다.

설계를 지배한 한 문장

깊이 추론은 33 ms 늦어도 아무도 모른다. 조명이 손을 33 ms 늦게 따라오면 즉시 티가 난다.

이 비대칭이 뒤의 거의 모든 결정을 만들었다 — 레이트 분리, 프레임 드롭 정책, 커맨드 버퍼 구조까지.

03핵심 결정과 근거

각각 대안이 있었고, 왜 그걸 버렸는지가 더 중요하다.

추론을 GPU 타임라인에 올린다

선택지는 둘이었다. Core ML로 Neural Engine을 쓰거나, Metal 4의 ML 인코더로 GPU에서 돌리거나. 상식적으로는 ANE가 유리하다 — 전용 하드웨어이고 GPU를 렌더링에 온전히 남겨준다. 그런데 측정해보니 반대였다.

Core ML .all (ANE)20.78 ms20.70 / 20.9348.1

26% 빠른 것도 이득이지만 진짜 이유는 따로 있다. Core ML 경로는 추론이 끝났음을 CPU가 알아야 다음 GPU 작업을 넣을 수 있다. Metal 4 ML 인코더는 같은 커맨드 버퍼 안에서 배리어 하나로 이어진다 — 추론 결과 버퍼를 다음 컴퓨트 셰이더가 그냥 읽는다. 프레임당 왕복 한 번이 사라지고, 지연의 분산(p10↔p90)도 줄어든다.

그래도 Core ML을 지운 건 아니다

DepthProvider 프로토콜 뒤에 두 경로를 다 남겼다. GPU가 렌더링으로 포화되는 순간이 오면 ANE 경로가 탈출구가 된다 — 20.8 ms지만 GPU 예산을 전혀 쓰지 않는다. 느린 쪽을 지우지 않는 이유는, 빠른 쪽이 항상 옳은 게 아니라 상황에 따라 다르기 때문이다.

완전 재조명이 아니라 가산 조명

"조명을 다시 계산한다"는 말은 두 가지로 읽힌다. 원본 조명을 제거하고 새로 칠하거나, 원본 위에 새 광원을 더하거나. 전자가 이상적이지만 albedo·normal·roughness·specular로 분해하는 intrinsic decomposition이 필요하고, 그건 SwitchLight급 파이프라인이라 실시간이 아니다.

그래서 후자를 택했다. 원본을 환경광으로 보존하고 가상 광원의 기여만 더한다. 물리적으로도 이게 맞다 — 방에 스탠드 하나를 켜는 것과 정확히 같은 연산이다. 다만 텍스처가 이중으로 밝아지는 걸 막으려고, 저주파 밝기를 나눠 pseudo-albedo를 만든다(Retinex 근사).

// 완전한 intrinsic 분해가 아니라, 가산 조명을 얹기 위한 최소한의 근사
float  sourceLuma = max(luminance(source), 1e-3);
float3 albedo     = source / pow(sourceLuma, 0.7);

광원 z는 피사체 기준 상대값

광원을 절대 좌표로 두면 사람이 조금만 앞뒤로 움직여도 조명이 얼굴 속으로 들어간다. 그래서 subjectDepth + depthOffset으로 잡았다. offset이 음수면 정면광, 양수면 역광이다. 이 한 줄이 "얼굴 앞에도 되고 뒤로도 넘어간다"를 성립시킨다.

static let nearestOffset:  Float = -0.35   // 카메라 바로 앞
static let farthestOffset: Float =  0.90   // 피사체 한참 뒤 → 완전한 역광

레이트를 쪼갠다

추론 15.4 ms를 60 fps(16.7 ms)에 욱여넣으면 예산이 남지 않는다. 그래서 깊이는 30 Hz, 렌더는 60 Hz로 돌리고 렌더 프레임의 절반은 직전 깊이맵을 재사용한다. 추론이 아직 돌고 있으면 새 캡처 프레임은 버린다 — 큐에 쌓으면 지연만 늘어난다.

04깊이: 상대성이라는 함정

단안 깊이 모델의 출력은 미터가 아니다. 이걸 모르면 조명이 펄럭인다.

Depth Anything V2가 내놓는 값은 affine-invariant inverse depth다. "이 픽셀이 저 픽셀보다 가깝다"는 순서는 믿을 수 있지만, 절대 거리도 아니고 프레임마다 스케일과 오프셋이 달라진다. 정지 화면에서도 미세하게 흔들린다.

3D 공간에 고정한 광원 기준으로 보면 이건 재앙이다. 씬 전체가 앞뒤로 펌핑하면서 그림자가 매 프레임 크기를 바꾼다. 해법은 배경을 앵커로 쓰는 것이다. 사람은 움직여도 배경은 안 움직이므로, person matte 바깥 픽셀만으로 직전 기준 프레임에 맞추는 robust affine fit을 돌린다. 중앙값·MAD 기반이라 RANSAC이 필요 없다.

// 배경 픽셀만으로 a, b를 구한다. 사람이 움직여도 스케일이 고정된다.
a = MAD(reference) / MAD(current)
b = median(reference) − a · median(current)
reference ← lerp(reference, a·current + b, 0.02)   // 아주 느린 갱신

플리커는 따로 잡는다. Video Depth Anything(CVPR'25)이 학습으로 푸는 문제지만 실시간엔 무겁다. 대신 edge-stopping 시간필터를 쓴다 — 색이 크게 변한 픽셀은 히스토리를 기각한다. 색 가중치를 빼면 사람이 움직일 때 깊이가 끌려와 고스팅이 생긴다. 이 항은 선택이 아니다.

macOS 하드 제약

깊이맵을 3D로 되돌리려면 초점거리 fx가 필요한데, macOS는 이걸 주지 않는다.

AVCaptureDeviceFormat.videoFieldOfView              → API_UNAVAILABLE(macos)
AVCaptureConnection.cameraIntrinsicMatrixDelivery*  → API_UNAVAILABLE(macos)

둘 다 iOS 전용이다. 그래서 얼굴 랜드마크의 동공간 픽셀거리와 성인 평균 IPD 63 mm로 추정하고, 3초치 중앙값을 모아 고정한 뒤 다시는 바꾸지 않는다. fx가 20% 틀려도 사람은 모른다. 프레임마다 변하면 즉시 티가 난다.

05그림자: POM과 같은 알고리즘

화면공간 깊이버퍼를 높이장으로 보면, 시차 폐색 매핑의 셀프섀도우와 스크린스페이스 섀도우는 같은 것이다.

가장 위험한 파라미터

thickness는 이 파이프라인에서 유일하게 양쪽 극단이 모두 완전한 실패인 값이다. 크면 배경 전체가 사람 뒤에 있다고 판정되어 화면이 까맣게 죽고, 작으면 그림자가 아예 안 생긴다. person matte 안쪽은 몸통 두께로, 배경은 얇게 주는 프라이어가 "가까운 물체가 빛을 가린다"를 성립시키는 유일한 장치다.

이 절의 전제가 뒤늦게 구현이 됐다

"높이장으로 보면 같은 것"이라고 써 놓고, 실제 구현은 오랫동안 씬을 3D 점구름으로 다뤘다 — 광선을 뷰공간에서 진행시키고 매 스텝 화면에 재투영하는 방식이다. 텍스처 공간 레이마칭으로 옮긴 것은 나중이다(§06-8).

부드러운 그림자는 공짜에 가깝다

광원 반경만큼 목표점을 원뿔 지터링하면 페넘브라가 생긴다. 샘플은 여전히 한 개다 — 노이즈는 인터리브드 그래디언트 노이즈로 깨고, 시간 누적으로 정리한다. 실제 광원처럼 가림물에서 멀어질수록 그림자가 부드러워진다.

06역광: 빛이 뒤로 갔을 때

광원을 얼굴 뒤로 넘기면 네 가지가 동시에 일어나야 실제처럼 보인다.

① 감쌈 확산 (wrap diffuse)

순수 램버시안은 N·L이 0이 되는 지점에서 딱 끊긴다. 피부는 표면 아래로 빛이 산란해 명암 경계가 훨씬 부드럽다. 이걸 한 줄로 근사한다.

float wrapped = saturate((dot(N, L) + wrap) / (1.0 + wrap));   // 피부는 wrap 0.3~0.5

② 림라이트

광원이 뒤에 있을 때만 켜진다. backness는 광원 방향이 시선 반대쪽을 향하는 정도다. 실루엣 픽셀은 정의상 광선이 곧바로 화면을 벗어나므로 그림자에 가려지지 않는다 — 이게 역광에서 테두리만 빛나는 이유다.

float backness = saturate(-dot(L, V));                // 1 = 완전한 역광
float rim      = pow(1.0 - saturate(dot(N, V)), rimPower);
accumulated   += rim * backness * matte * lightColor * intensity;

③ 투과 산란

귀와 머리카락처럼 얇은 부위는 빛이 통과해 붉게 비친다. 실제로는 subsurface scattering이지만 실시간에서는 Frostbite 계열의 값싼 근사로 충분하다 — 빛 방향을 노멀로 살짝 왜곡해 뒤에서 본다. "얇음"은 깊이 기울기로 추정한다. 실루엣 근처에서 기울기가 크다.

float3 scatterDir = normalize(-L + N * 0.25);
float  scatter    = pow(saturate(dot(V, scatterDir)), 4.0);
accumulated      += scatter * thinness * matte * translucency * lightColor;

④ 광원 글로우의 깊이 테스트

가장 작지만 체감이 가장 큰 항목이다. 광원을 나타내는 빛무리를 그릴 때 씬 깊이와 비교해서, 머리보다 멀면 그리지 않는다. 손으로 조명을 얼굴 뒤로 넘기면 빛무리가 머리 뒤로 사라진다. 이 한 장면이 "이게 진짜 3D 공간에서 계산되고 있다"를 말없이 증명한다.

bool visible = (light.position.z < sceneZ + bias) || sceneZ <= 1e-4;
if (visible) glow += exp(-d*d*900.0) * lightColor * intensity;
공짜로 얻는 것

손이 화면 안에 있으면 손도 깊이맵에 있다. 그래서 손 그림자가 뺨을 가로지른다. 별도 구현이 없다 — 레이마칭이 손을 그냥 하나의 가림물로 취급할 뿐이다. 같은 이유로 핀치의 z도 공짜다: 깊이맵을 손 위치에서 샘플하면 된다.

06-1핀치: 손이 곧 컨트롤러

센서를 하나도 더 쓰지 않고 3D 위치를 얻는 법.

z를 어디서 가져오는가

손으로 조명을 잡으려면 손의 3차원 위치가 필요하다. x·y는 Vision이 주지만 z는? 깊이 센서도, 스테레오도 없다. 답은 이미 갖고 있었다 — 손도 프레임 안에 있으므로 깊이맵이 손의 거리를 알고 있다. 핀치 지점에서 같은 깊이맵을 샘플하면 끝이다.

여기서 한 번 틀렸다

처음엔 핀치 지점의 한 픽셀을 그냥 읽으려 했다. 손끝은 얇다. 깊이맵 해상도(518×392)에서 손가락 끝은 몇 픽셀이고, 그 주변은 전부 배경이다. 평균이나 중앙값을 쓰면 배경이 섞여 광원이 손보다 한참 뒤로 밀린다.

해법은 가장 가까운 쪽 분위수다. 5×5 이웃을 정렬해 상위 20% 지점을 쓴다 — 역깊이는 클수록 가까우므로, 이 값은 "이 근방에서 카메라에 가장 가까운 것들"을 뜻한다. 손이 있으면 손을, 없으면 배경을 자연스럽게 고른다.

neighborhood.sort()
let index = min(Int(Float(neighborhood.count) * 0.8), neighborhood.count - 1)
return neighborhood[index]   // 평균도 중앙값도 아닌 이유가 여기 있다

깊이 버퍼를 CPU가 읽게 하는 값

이 샘플링에는 CPU 접근이 필요하다. 텐서를 .private에서 .shared로 바꿨는데, 보통은 성능 저하를 각오해야 하는 변경이다. 그런데 Apple Silicon은 통합 메모리라 측정해보니 차이가 없었다(15.1~15.6 ms로 동일). 추측 대신 재보고 결정했다.

거울상의 함정 — 한쪽만 뒤집어야 한다

프리뷰는 거울상이다. 사용자가 거울에 익숙하기 때문이다. 그러면 핀치 좌표도 뒤집어야 할까? 아니다.

  • 핀치는 보정하지 않는다. 핀치 좌표와 렌더링이 둘 다 원본 카메라 좌표계이고 프리뷰에서 함께 뒤집히므로, 사용자 눈에는 손과 조명이 같은 자리에 보인다.
  • 마우스는 보정해야 한다. 사용자가 이미 뒤집힌 화면을 보고 찍기 때문이다.

양쪽을 다 뒤집거나 다 안 뒤집으면 둘 중 하나가 반대로 간다. 그래서 보정은 마우스 입력 지점 한 곳에서만 한다. 이 규칙을 코드 주석에 못 박아두지 않으면 반드시 다시 틀린다.

손 추적과 깊이 추론은 서로 기다리지 않는다

둘 다 무거운 작업이다(Vision 수 ms, 추론 15 ms). 하나의 게이트로 묶으면 느린 쪽이 빠른 쪽을 끌어내린다. 그래서 독립된 in-flight 게이트를 두고 각자 자기 속도로 돌게 했다. 진행 중이면 새 프레임은 큐에 쌓지 않고 버린다 — 쌓으면 지연만 늘어난다.

실측 (손 모드 26초) 
손=보임  핀치=잡음  깊이샘플 d=0.75~0.91  광원 z=0.30~1.50 m
캡처 30fps · 깊이 18~19 ms · cam/depth/relit 모두 OK

z가 0.30~1.50 m를 오간다는 것은 정면광에서 완전한 역광까지 전 범위를 손으로 커버한다는 뜻이다.

06-2화질: "카메라 같지 않다"의 해부

한 가지 증상에 원인이 넷이었다. 하나씩 지워야 보인다.

리라이팅이 돌기 시작하자 결과가 흐릿하고 색이 뜬 합성 이미지처럼 보였다. "조명 알고리즘이 나쁜가" 싶었지만, 실제로는 조명과 무관한 문제가 셋 섞여 있었다.

증상원인수정
흐릿함 출력이 518×392. 카메라 해상도까지 3배 확대되고 있었다 조명만 1554×1176로 계산. 깊이맵은 저주파라 저해상도로 둬도 티가 안 난다

출력 해상도가 카메라 해상도가 아니었다

3배 확대를 고친 뒤에도 "카메라 질감이 아니다"가 남아 있었다. 남은 원인은 출력 크기가 1554×1176으로 고정돼 있었다는 것이다. 실제 카메라는 1552×1552로 들어온다. 가로는 거의 같지만 세로가 잘리고, 그 과정에서 다운샘플과 크롭이 동시에 일어났다. 확대만 없앴을 뿐 여전히 리샘플을 한 번 더 거치고 있었던 셈이다.

수정은 순서를 바꾸는 것이다. 캡처를 먼저 만들어 activeDimensions로 실제 해상도를 읽고, 그 값에 맞춰 파이프라인을 생성한다. 상한은 1920×1440으로 둔다 — 레이마칭 비용이 픽셀 수에 선형이라 GPU 예산을 지켜야 한다.

카메라 포맷도 sessionPreset에 맡기지 않고 명시적으로 고른다. 맡기면 시스템이 30 fps 저해상도 포맷을 줄 수 있다. 선택 기준은 프레임레이트 우선, 그다음 해상도다 — 60 fps 소스가 손 인터랙션의 체감에 직결되기 때문이다.

로그 확인 
카메라 1552x1552 → 출력 1552x1552

픽셀 수는 1.83M에서 2.41M으로 31% 늘었지만 깊이 처리는 오히려 빨라졌다. 이유는 §09-1에 있다.

그리고 흰 후광

해상도와 색을 고치고 나니 새 문제가 보였다 — 얼굴과 손 둘레에 흰 테두리가 탔다. 범인은 역광의 투과 산란이었다. "얇은 부위"를 깊이 기울기로 추정했는데, 실루엣 경계가 가장 큰 기울기를 갖는다. 귀와 실루엣을 구분하지 못한 것이다.

// 고치기 전 — 기울기가 클수록 얇다고 봤다
return saturate(gradient * 40.0);                        // ✗ 실루엣이 최대값

// 고친 후 — 대역 통과. 실루엣은 얇은 게 아니라 끊긴 것이다
float rising  = smoothstep(0.002, 0.020, gradient);       // 평평한 면은 얇지 않다
float falling = 1.0 - smoothstep(0.045, 0.110, gradient); // 절벽도 얇지 않다
return rising * falling;

같은 이유로 림라이트도 절벽에서 억제하고, AO의 가림 판정에도 거리 상한을 뒀다 — 실루엣 너머의 배경은 "가림"이 아니라 다른 물체다.

이 버그를 어떻게 찾았나

앱 창을 눈으로 보는 것만으로는 원인을 나눌 수 없었다. 그래서 재조명 결과를 PNG로 덤프하는 진단 경로를 만들었다. 정지 이미지로 보니 후광이 실루엣을 정확히 따라간다는 게 한눈에 보였고, 거기서 기울기가 범인임이 나왔다. 실시간 화면에서는 절대 못 봤을 것이다.

06-3깊이맵이 거짓말하는 순간

광원을 머리 뒤로 보내면 오히려 머리 앞에 붙어 고정되던 버그.

핀치의 z를 깊이맵에서 읽는 설계는 우아했다. 손도 프레임 안에 있으니 공짜라고 썼다. 그런데 손이 가려지는 순간 이 전제가 무너진다.

손을 머리 뒤로 가져가면, 화면의 그 지점에서 깊이맵이 읽는 것은 손이 아니라 머리다. 손이 머리에 가려졌으니 당연하다. 게다가 "가장 가까운 쪽 분위수"를 쓰므로 더 가까운 머리를 확실하게 고른다. 결과적으로 광원이 머리보다 7cm 앞에 고정된다 — 뒤로 보내려는 의도와 정확히 반대다.

튜닝으로는 못 고친다

임계값을 조정하거나 샘플 반경을 키워도 소용없다. 가려진 물체의 깊이는 2.5D 깊이맵에 애초에 존재하지 않는 정보다. 다른 신호가 필요하다는 뜻이지, 같은 신호를 더 잘 쓰면 되는 문제가 아니다.

가림에 영향받지 않는 신호

손목에서 중지 MCP까지의 픽셀 거리는 1/Z에 비례한다. 그리고 이 값은 손이 무엇에 가려져 있든 상관없다 — Vision이 손을 보는 한 유효하다.

// 핀치 시작 순간에만 깊이맵을 믿는다. 이때는 손이 앞에 나와 있어 가려질 일이 없다.
if (!isGrabbing || referenceHandScale <= 0) {
    referenceHandScale = handScale
    referenceHandZ = depthZ
    return depthZ
}
// 이후에는 크기 변화만 본다. 작아 보이면 멀어진 것이다 — 가려져 있어도 성립한다.
let estimated = referenceHandZ * (referenceHandScale / handScale)

깊이맵은 한 번의 캘리브레이션에만 쓰고, 추적은 손 크기가 맡는다. 두 신호의 강점이 정확히 상보적이다 — 깊이맵은 절대 거리를 알지만 가림에 약하고, 손 크기는 절대 거리를 모르지만 가림에 강하다.

이후 뒤집혔다 — 이 결정은 지금 코드에 없다

위의 손 크기 외삽은 제거됐다. 가림에 강하다는 장점은 실재했지만, 손 크기는 거리만의 함수가 아니었다 — 손을 돌리거나 주먹을 쥐면 같은 거리에서도 크기가 크게 변해 z가 틀렸다. 그 결과가 다시 "광원이 오브젝트 앞에 붙는" 증상이었다. 지금은 깊이맵만 쓴다. 무엇을 놓쳤는지는 §06-5에 적었다.

광원 수명 — 놓으면 사라진다

추적을 아무리 다듬어도 남는 증상이 있었다. 손을 놓으면 광원이 마지막 자리에 그대로 남는다. 그 자리가 하필 손등 뒤나 얼굴 속이면 "왜 저기 박혀 있지"가 된다. 깊이 추정을 더 정교하게 만들어 이상한 자리에 박히는 경우를 줄이는 길도 있었다.

대신 그 상태가 존재할 수 없게 만들었다. LightRig.isLit — 광원은 핀치 중일 때만 존재한다. 놓으면 fill()이 lightCount 0을 내보내고 광원은 즉시 사라진다. 잘못된 위치에 남은 광원이라는 상태 자체가 없어진다.

설계 교훈

상태를 고치는 것보다 상태를 없애는 쪽이 견고하다. 추정을 개선하는 방향은 "얼마나 좋아졌나"가 항상 확률적이지만, 상태를 제거하는 방향은 증상이 발생할 수 없다는 것을 코드에서 읽을 수 있다.

단, 마우스 모드는 항상 켜 둔다 — 거기서는 커서가 곧 광원이라 이 규칙이 자연스럽게 성립한다.

이 결정은 이후 뒤집혔다 — 놓아도 광원은 남는다

지금은 핀치를 놓아도 광원이 마지막 자리에 그대로 남는다(§06-8). 위의 isLit 논리는 여전히 옳지만, 그 옳음이 쓰는 사람의 감각과 어긋났다. 조명을 잡았다 놓는 동작에서 기대되는 것은 "빛이 꺼진다"가 아니라 스탠드를 그 자리에 놓아둔다였다. 놓을 때마다 어두워지면 위치를 조정하는 일 자체가 안 된다.

대신 광원이 이상한 자리에 박히는 문제는 다른 쪽에서 막았다 — §06-5의 "모르면 움직이지 않는다"(가림이 의심되면 광원을 두고 손만 놓는다)와, 광원을 항상 핀치보다 카메라 쪽에 띄우는 규칙이다. 즉 상태를 없애는 대신, 그 상태가 나쁜 값을 갖지 못하게 했다.

기록 목적으로 위 서술은 지우지 않는다. 당시 판단의 근거는 실제로 저것이었고, 뒤집힌 이유는 견고함이 아니라 사용감이었다는 것까지가 이 결정의 전부다.

06-4안정화: 떨림을 8배 줄이기

정지해 있어도 깊이는 프레임마다 다르게 나온다. 그 떨림이 노멀과 그림자를 타고 증폭된다.

단안 깊이 추론은 프레임마다 독립적으로 돈다. 입력이 거의 같아도 출력은 미세하게 다르고, 조명 계산이 그 차이를 그대로 받는다. 먼저 떨림을 수치로 잡았다 — 연속 프레임 간 깊이 변화의 중앙값(16 px 서브샘플, EMA)을 플리커 지표로 삼고, 같은 세션의 앞 15초를 안정화 OFF, 뒤 15초를 ON으로 A/B를 돌렸다 (M5, --autostart, 정지 자세).

OFF (앞 15초)0.002080.002900.004390.002840.00425
ON (뒤 15초)0.000490.000300.000740.000350.00036

edge-stopping 시간필터 — 어디서 섞기를 멈출지

구현은 시간축 블렌딩이다(Stabilize.metal). 히스토리를 현재 깊이에 섞되, 픽셀마다 히스토리를 얼마나 믿을지를 두 가중치로 정한다.

// 히스토리 신뢰도 = 색 가중치 × 깊이 가중치 × temporalBlend
w = exp(−|Δc|²/σc) × exp(−|Δd|/σd) × 0.85
// Δc: 현재 프레임과 히스토리의 색 차이, Δd: 깊이 차이

깊이 가중치만으로는 안 된다. 색 가중치를 빼면 움직일 때 고스팅이 생긴다 — 이전 프레임의 깊이가 잔상으로 끌려온다. 색은 물체가 지나간 픽셀에서 확실하게 변하므로, 색이 변한 곳에서 블렌딩을 끊는 것이 이 필터가 "edge-stopping"인 이유다.

배경 앵커 — 프레임 전체가 함께 출렁일 때

픽셀 단위 떨림과 별개로, 상대 깊이는 프레임 전체의 스케일·오프셋이 함께 출렁인다. 그래서 시간필터와 함께 affine 정합을 둔다. 앵커는 하위 45% 역깊이 — 즉 배경만 쓴다. 전경(사람·손)은 실제로 움직이는 대상이라 정합 기준으로 삼으면 진짜 움직임까지 지워버리고, 배경은 웹캠 장면에서 사실상 고정이기 때문이다. 피팅은 중앙값/MAD 기반 robust fit이다.

기준(레퍼런스)은 rate 0.02로 아주 느리게 갱신한다. 빠르게 갱신하면 앵커가 같이 흘러간다 — 잡으려는 드리프트를 기준이 따라가버리면 정합이 무의미해진다. 폭주 방지도 있다: 피팅된 a가 기준의 0.5~2.0배를 벗어나면 그 프레임은 보정하지 않는다.

이 패스를 단일 커맨드 버퍼에 끼워 넣다가 인코딩 순서 해저드를 하나 만들었다 — §07에 적었다.

정직한 성능 관찰 — 이후 해결

안정화 ON 구간 후반에 깊이 처리 시간이 20.7 ms → 33.5 ms까지 변동했다. 30 fps 예산(33.3 ms)의 경계다. 당시에는 세그멘테이션(15 Hz)과의 간섭으로 추정했고, 그 추정은 틀렸다. 구간을 쪼개 재보니 콜드 스타트였다 — §09-1.

06-5추측을 없앴다

광원이 오브젝트 앞에 붙어 고정되던 버그. 원인은 알고리즘이 아니라 보이지 않는 것을 추측한 코드였고, 그런 코드가 두 군데 있었다. 셋째는 나중에 드러났다.

증상은 §06-3과 같은 문장이다. 핀치한 손을 오브젝트 뒤로 옮기면 광원이 오브젝트 앞에 붙어 고정된다 — 뒤로 보내려는 의도와 정확히 반대다. 같은 증상이 다시 나왔다는 것은 그때의 해법이 원인의 일부였다는 뜻이었다.

추측 1 — 손 크기 외삽

§06-3에서 도입한 신호다. 손이 가려져도 wrist↔middleMCP 픽셀 거리로 z를 이어서 추정했다. "Vision이 손을 보는 한 유효하다"는 논리는 깔끔했고, 깊이맵(절대 거리를 알지만 가림에 약함)과 상보적이라는 그림도 매력적이었다.

놓친 것은 이것이다. 손 크기는 거리만의 함수가 아니다. 손을 돌리거나 주먹을 쥐면 같은 거리에서도 wrist↔middleMCP 거리가 크게 변한다. 그러면 referenceHandScale / handScale이 그대로 z 오차가 된다. 가림에는 강했지만 자세에는 약한 신호였고, 핀치하는 손은 계속 자세가 바뀐다.

제거했다. 이제 z는 깊이맵만 쓴다.

추측 2 — 손을 놓쳤을 때 마지막 핀치 상태 유지

Vision이 손을 못 찾은 프레임에서 직전 핀치 상태를 유지하고 있었다. 깜빡임을 견디려는 코드였지만, 그 대가는 광원이 마지막 자리에 남는다는 것이다. 그 자리가 하필 오브젝트 앞이면 정확히 이 버그가 된다.

손이 안 보이면 즉시 핀치를 놓는다.

가림 경계는 감지해서 손을 뗀다

세 번째 경우가 남는다. 손과 그 뒤의 물체가 한 샘플 창에 같이 잡히는 순간이다. 이때는 어느 쪽을 골라도 틀릴 수 있다 — 가장 가까운 쪽 분위수(§06-1)든 중앙값이든 마찬가지다. 그래서 고르지 않기로 했다. 핀치 지점 5×5 이웃 깊이의 퍼짐(최대−최소)이 0.12를 넘으면 여기는 가림 경계라고 표시하고, 광원을 움직이지 않는다.

neighborhood.sort()
let depth = neighborhood[index]

// 이웃 깊이의 퍼짐이 크면 손과 뒤 물체가 한 창에 같이 잡힌 것이다
let spread = neighborhood[neighborhood.count - 1] - neighborhood[0]
return (depth, spread < 0.12)   // .1 = depthIsReliable

// 광원 갱신 쪽
guard pinch.depthIsReliable else { return }   // 틀린 z로 옮기느니 그 자리에 둔다

그래도 남아 있었다 — 가려진 관절도 Vision은 계속 준다

위 셋을 고친 뒤에도 같은 증상이 드물게 남았다. 남은 경로는 이것이다. 핀치하는 엄지·검지 끝이 손등이나 다른 손가락에 가려져도 Vision은 관절 좌표를 계속 추정해 준다. 좌표가 오니 코드는 손이 보인다고 믿고, 그 화면 좌표에서 깊이맵을 읽으면 읽히는 것은 손끝이 아니라 손끝을 가린 쪽이다. 결과는 또 광원이 오브젝트 앞에 뜨는 것이다.

이웃 퍼짐(spread)으로는 못 잡는다. 가린 쪽 표면이 매끄러우면 5×5 창 안의 깊이가 고르게 나오기 때문이다. 다른 신호가 필요했고, 이번엔 손은 한 덩어리라는 사실을 썼다 — 손목 · indexMCP · middleMCP · ringMCP는 서로 가리기 어려운 관절들이다. 이 넷의 깊이 중앙값이 손 전체가 어디쯤 있는지를 말해 준다. 손끝은 손바닥보다 카메라에 가깝거나 비슷하다. 유독 멀면 가려진 것이다.

// 손바닥 쪽 관절들 — 서로 가리기 어려워 기준으로 삼을 만하다
let names: [HumanHandPoseObservation.JointName] = [.wrist, .indexMCP, .middleMCP, .ringMCP]

// 역깊이라 값이 클수록 가깝다. 손끝이 손바닥보다 크게 멀면(작으면) 가림이다.
return pinchDepth > median - 0.10   // false면 depthIsReliable = false → 광원을 움직이지 않는다

판단 근거가 없으면(신뢰도 0.4를 넘는 앵커 관절이 2개 미만) 통과시킨다. 막을 수 없는 경우까지 막으려 들면 이번엔 정상 동작이 끊긴다.

스냅 애니메이션도 지웠다

잡는 순간 광원이 손끝으로 날아가는 연출이 있었다. 보기 좋으라고 넣은 것인데, 그 사이 프레임에서는 광원이 손과 다른 곳에 있다는 뜻이다. 그리고 이 버그가 눈에 띄던 순간이 정확히 거기였다. 지금은 보간 없이 즉시 배치한다.

이번 단계의 원칙

광원이 엉뚱한 곳에 붙어 있는 것보다, 잠깐 사라지는 쪽이 낫다. 추측은 항상 "대부분의 경우 맞다"로 정당화되지만, 사용자가 기억하는 것은 틀린 순간이다. 틀린 자리에 고정된 광원은 사용자가 조작으로 되돌릴 수 없고, 사라진 광원은 다시 잡으면 된다.

이것은 §06-3의 "상태를 고치는 것보다 상태를 없애는 쪽이 견고하다"와 같은 방향이다. 다만 그때는 광원의 수명에만 적용했고, z 추정에는 적용하지 못했다.

검증

손이 프레임을 벗어나면 즉시 핀치=놓음, z는 그 자리에 고정된다. 깊이 처리 17.8 ms 유지, 크래시 없음.

06-6하이라이트가 점이었던 이유

피부에 뜬 반사광이 흰 dot으로 보였다. 세기도 거칠기도 범인이 아니었다 — 광원 반경이 스펙큘러 계산에 아예 들어가 있지 않았다.

광원에는 radius가 있었다. 그런데 그 값은 그림자 페넘브라를 부드럽게 하는 데만 쓰였고, 스펙큘러는 광원을 수학적 점으로 계산하고 있었다. 점광원의 하이라이트는 점이다 — 코드가 시킨 그대로 나온 결과였다. 실제 촬영에서 얼굴에 뜨는 하이라이트는 소프트박스의 크기와 모양을 그대로 반사한다. "조명이 어색하다"의 원인이 조명 모델이 아니라 빠진 입력이었던 셈이다.

① 구를 대표점 하나로 — Karis representative point

면광원을 제대로 적분하면 실시간이 아니다. 대신 반사 벡터에서 광원 구에 가장 가까운 점을 골라 그 점을 광원으로 친다. 하이라이트가 구의 실루엣을 따라 번지는 근사다.

// ✗ 고치기 전 — 광원 중심 하나로 하프벡터를 만든다. radius는 쓰이지 않는다
float3 H = normalize(L + viewDirection);

// ✓ 고친 후 — 반사 벡터에 가장 가까운 구 표면 점을 광원으로 삼는다
float3 reflectDir  = reflect(-viewDirection, normal);
float3 centerToRay = dot(toLight, reflectDir) * reflectDir - toLight;
float3 closestPoint = toLight + centerToRay * saturate(light.radius / max(length(centerToRay), 1e-4));
float3 specL = normalize(closestPoint);

② 넓힌 만큼 어두워야 한다

대표점만으로는 부족하다. 광원이 크고 가까울수록 로브 자체가 넓어져야 한다. 그래서 거칠기를 광원 크기만큼 키우는데, 여기에 에너지 항을 같이 넣지 않으면 반경을 키워도 하이라이트 크기가 그대로다. 로브를 넓히면서 정점 밝기를 그대로 두면 포화된 흰 픽셀이 남아 여전히 점으로 보이기 때문이다.

float sphereWiden = saturate(light.radius / (2.0 * max(distance, 1e-3)));
float roughness   = saturate(baseRoughness + sphereWiden);
float energy      = 1.0 / (1.0 + sphereWiden * 4.0);   // 넓어진 만큼 어두워져야 한다

③ 이중 로브 — 피부는 층이 둘이다

피부는 얇은 기름막(좁고 밝음)과 그 아래 층(넓고 흐림)이 겹쳐 반사한다. 단일 GGX 로브로 그리면 유리처럼 보인다 — 반사가 한 겹이라 표면이 딱딱해 보인다.

float D = mix(ggxDistribution(NdotH, roughness * 1.6),
          ggxDistribution(NdotH, roughness * 0.7), 0.35);

여기에 기본 반경을 0.06 → 0.18 m로 올렸다. 스팟에서 소프트박스로 바꾼 것이다. ①②가 들어오기 전에는 반경을 올려도 그림자만 부드러워졌지 하이라이트는 변하지 않았다.

④ 완벽한 원을 흩는다 — 노멀 디테일

남은 문제가 하나 더 있었다. 518×392 깊이맵은 얼굴을 매끄러운 타원으로 만든다. 그런 표면 위의 하이라이트는 수학적으로 완벽한 원이 되고, 사람은 그걸 즉시 CG로 읽는다. 실제 피부는 미세 요철이 하이라이트를 흩는다.

깊이맵에 없는 그 요철은 카메라 영상에 있다. 피부는 대체로 램버시안이므로 루마의 고주파는 지오메트리 고주파에 가깝다. 그래서 루마 고주파의 기울기를 노멀에 실었다 — 값이 아니라 기울기여야 노멀이 기울어진다.

n.xy += (slope * 18.0 + highPass) * u.detailStrength;
n = normalize(n);

재투영이 실제로 하는 일은 스케일 정합이다

"height map reprojection"이라는 말이 처음에는 기하 변환처럼 들렸지만, 하는 일은 단위를 맞추는 것이다. 화면 uv 1단위가 실제 몇 미터인지, 높이 1단위가 몇 미터인지를 일치시켜야 광선의 기울기가 물리적으로 옳아진다. 그 비율 하나가 heightToUV다.

그리고 높이는 미터가 아니라 [0,1]로 정규화했다.

// ✗ 미터를 그대로 쓰면: 깊이 범위(수 미터)가 화면 폭(수십 cm)보다 훨씬 크다.
//   작은 깊이 노이즈가 거대한 기울기가 되고, 그 기울기가 노멀과 AO를 타고 증폭된다.
float h = farDistance - z;

// ✓ uv와 같은 [0,1]에 둔다. 실제 종횡비는 heightToUV가 따로 들고 있는다.
float h = saturate((farDistance - z) * heightScale);

단위를 바꾸면 그에 딸린 상수가 전부 바뀐다 — 세 번 검은 화면을 만들었다

커널 구조를 바꾸는 것보다 미터를 전제로 튜닝해 둔 상수들을 찾아내는 쪽이 오래 걸렸다. 셋 다 컴파일도 되고 실행도 됐다. 화면만 죽었다.

화면 전체가 검게 죽음 — AO가 전 픽셀에서 포화

① thickness와 AO 반경이 미터 기준 그대로였다

높이가 [0,1]이 됐는데 비교 대상인 두께·AO 반경은 미터 시절 값이었다. 모든 이웃이 "차폐"로 판정되어 AO가 전부 1에 붙었다.

→ 정규화 높이 기준으로 다시 잡았다.

또 검은 화면 — 이번엔 조명 기여가 0에 수렴

② 감쇠식 계수가 미터 거리를 전제하고 있었다

1/(1 + 6d + 12d²)는 d가 미터일 때 맞춘 값이다. 거리가 uv(0~1)로 바뀌자 같은 물리 거리가 훨씬 작은 수가 됐어야 하는데, 계수는 그대로라 분모가 커진 쪽으로 어긋나 기여가 0으로 갔다.

→ 1/(1 + 1.5d + 2.5d²)로 교정. 화면이 돌아왔다.

평평한 배경에 자글자글한 자기그림자

③ shadowBias 없이 delta > 0만 검사했다

광선이 출발한 표면 자신이 첫 스텝에서 가림물로 잡힌다. 높이가 [0,1]로 좁아지면서 수치 여유가 함께 줄어든 것이 표면화한 계기였다.

→ shadowBias < delta < thickness로 하한을 넣었다. §05의 두께 창에 바닥이 하나 더 생긴 셈이다.

추측을 멈추고 각 항을 따로 뽑았다

두 번째 검은 화면에서 "높이장이 잘못 나온 것 아닐까"를 붙잡고 있었다. 그럴듯했지만 증거가 없었다. --debug 1~4로 원본 · AO · 높이장 · 노멀을 각각 화면에 그대로 출력하게 만들고 하나씩 봤다.

화면에 격자 모양 블록. 크기가 정확히 16×16의 배수

같은 커널이 heightTexture를 읽으면서 동시에 쓰고 있었다

세그멘테이션이 꺼져 있을 때(§07-3 이후 기본값) 매트 입력 자리에 바인딩할 텍스처가 없어서 heightTexture를 폴백으로 꽂았다. 그런데 그 커널이 쓰는 출력도 같은 텍스처였다. 스레드그룹마다 읽기와 쓰기의 순서가 달라진다.

→ 단서는 블록 크기가 컴퓨트 타일(16×16)과 일치한다는 것이었다. 화면에 스레드그룹 경계가 그대로 보인다면 원인은 셰이더 수식이 아니라 디스패치 단위의 경쟁이다. 전용 더미 텍스처를 만들어 입력과 출력을 분리했다.

핀치 동작 세 가지를 함께 정리했다

  • 놓아도 광원은 마지막 자리에 남는다. 조명 스탠드를 놓아두는 감각이다. 이것은 §06-3에서 내린 반대 방향의 결정을 뒤집은 것이다.
  • 손이 안 보이면 위치를 예측하지 않는다. 잡은 상태만 풀고 광원은 그대로 둔다 — §06-5의 "모르면 움직이지 않는다"는 그대로 지킨다.
  • 광원은 항상 핀치보다 카메라 쪽에 뜬다(정규화 높이 +0.05). 같은 높이면 광원이 손에 파묻히고, 뒤에 두면 손이 광원을 가린다. 둘 다 "잡고 있다"는 느낌을 깬다.
정직하게 — 이 재구성은 아직 느리다

측정값은 gpu 22.6~24.3 ms다. POM 이전(§09의 16.2 ms 예산 배분)보다 느리다. 스텝당 투영은 없앴지만, 별도 AO 패스를 지우면서 AO를 출력 해상도(2.4 M 픽셀)에서 매 픽셀 계산하는 구조가 됐고 그 비용이 이득을 상쇄했다.

AO를 높이장 해상도(518×392)로 내리면 되찾을 수 있다 — 아직 안 했다. 회수 계획은 §12에 적었다.

Tensor Descriptor Validation

device-alloc 텐서는 strides가 nil이어야 한다

MTLDevice.makeTensor(descriptor:)에 strides를 주면 거부된다. 그런데 셰이더가 읽으려면 패딩 제어가 필요하다.

→ MTLBuffer.makeTensor(descriptor:offset:)로 buffer-backed 텐서를 만든다.

Stride at index 1 should be 64-byte aligned

ML usage 텐서는 행이 패딩된다

f32 518열 = 2072 B가 2112 B(528 elem)로 늘어난다. 셰이더가 width로 인덱싱하면 행마다 10칸씩 밀려 비스듬히 찢어진 그림이 나온다.

mlir module expected element type f32 but received f16

변환된 그래프는 f32 입출력을 기대한다

모델 가중치가 f16이라 f16 텐서를 물렸더니 MPSGraph가 assert로 죽었다.

→ 입출력 텐서는 f32로. 내부 연산 정밀도와 인터페이스 정밀도는 별개다.

세마포어에서 영원히 대기

MTL4CommitOptions.addFeedbackHandler를 걸어도 콜백이 오지 않는다.

Metal 4는 자동 레지던시가 없다

버퍼·힙·텍스처를 명시적으로 상주시켜야 한다. 매 프레임 바뀌는 카메라 텍스처가 특히 곤란하다.

→ 고정 리소스는 큐에 붙인 MTLResidencySet, 카메라 텍스처는 commandBuffer.useResidencySet()로 프레임 단위 처리.

배리어 없는 RAW 해저드 — 시각화가 안정화 결과를 먼저 읽음

단일 커맨드 버퍼에서는 인코딩 순서가 곧 의존성 선언이다

시각화 패스가 stabilizedBuffers[historyIndex]를 읽는데, 같은 커맨드 버퍼에서 안정화 패스가 그 버퍼에 나중에 쓰도록 인코딩돼 있었다. 첫 프레임엔 비초기화 메모리를 읽고, 이후엔 GPU 재정렬에 따라 정의되지 않은 동작이다. 단일 커맨드 버퍼 설계는 CPU 동기화가 없어 빠르지만, 패스를 추가할 때 "어디에 끼워 넣는가"가 그대로 정확성 문제가 된다.

→ 안정화를 시각화 앞으로 옮기고, 주석에 "반드시 안정화 뒤에 인코딩"을 박았다.

드래그 좌표를 얻으려고 GeometryReader로 Metal 뷰를 감쌌더니 크기 협상이 재귀했다. GeometryReader는 부모 제안을 그대로 소비하는데, 그 안의 NSViewRepresentable이 다시 크기를 되묻는 구조가 된다.

→ 렌더 파라미터를 메인 액터에서 스냅샷해 락으로 보호된 RenderState에 넣고, draw는 그것과 FrameStore만 읽는 완전한 nonisolated로 만들었다.

두 건의 공통점

둘 다 컴파일러가 잡아주지 않는 계약 위반이었다. Swift 5 모드에서는 액터 격리가 경고조차 아니고, 레이아웃 재귀는 타입 시스템 밖의 일이다. 크래시 리포트의 스택을 끝까지 읽는 것 말고는 방법이 없었다.

가장 비쌌던 버그: 이중 정규화

깊이맵이 나오긴 나오는데, 가운데가 멀고 가장자리가 가까운 터널 모양이 나왔다. 합성 입력이라 모델이 헷갈린 거라고 넘길 뻔했다. 그런데 Core ML과 대조해보니 상관계수가 −0.34였다. 음의 상관 — 우연이 아니라 반대로 계산하고 있었다.

답은 모델 그래프 안에 있었다. 컴파일된 model.mil의 첫 두 연산이 이것이다.

sub(x = image, y = [123.675, 116.28, 103.53])          // ImageNet 평균 × 255
mul(x = ...,   y = [1/58.395, 1/57.12, 1/57.375])      // 1 / (std × 255)

정규화가 이미 그래프 안에 있었다. 그래프는 0–255 원본 RGB를 기대하는데, 나는 0–1로 스케일한 뒤 ImageNet 정규화를 한 번 더 걸고 있었다. Core ML 경로에서는 이 전처리가 모델에 감춰져 있어 보이지 않았고, mtlpackage로 변환하면 입력이 생짜 텐서가 되면서 내가 책임져야 하는 부분이 된 것이다.

// 고치기 전 — 이중 정규화
float3 rgb = source.sample(s, uv).rgb;
float3 normalized = (rgb - kImageNetMean) / kImageNetStd;   // ✗

// 고친 후 — 그래프가 알아서 한다
float3 rgb = source.sample(s, uv).rgb * 255.0;              // ✓

그 다음 버그: fp16을 fp32로 읽기

고쳤는데도 상관계수가 −0.28이었다. 이번엔 파이프라인이 아니라 검증 코드가 틀렸다. Core ML 출력은 Grayscale16Half인데 Float(4바이트)로 읽고 있었다. 포맷 코드 1278226536을 ASCII로 풀면 "L00h" — half다.

고치자 r = 1.00000이 나왔다. 검증 도구도 검증해야 한다는 걸 비싸게 배웠다.

--no-matte 4회 시작 사이클 → 크래시 0. 세그멘테이션의 첫 모델 로드가 방아쇠라는 것이 실험으로 확정됐다. 인자는 지웠다가 다시 필요해질 것이므로 이등분 도구로 남겨뒀다.

진단 도구가 크래시를 만들면 진단이 불가능하다

③이 가장 비쌌다. 원인 ①·②를 좁히는 동안 --autostart 루프가 계속 자기가 만든 크래시를 섞어 넣었다. 관측하려고 켠 것이 관측 대상을 바꾸고 있었으니 "고쳤는데 또 죽는다"가 반복될 수밖에 없었다. 관측 코드는 관측만 해야 한다 — 상태를 흔들어야 하는 A/B는 런마다 조건을 고정하는 쪽으로 옮긴다.

정직하게 — ②는 완전 차단이 아니다

워밍업은 프레임워크 내부에서 나는 크래시를 우리 코드에서 막는 것이 아니다. 두 모델의 첫 로드가 겹치는 노출 시간을 최소화하는 완화일 뿐이다. Espresso 런타임 안의 등록 경로 자체는 우리가 손댈 수 없다.

죽은 장치를 붙잡고 있는 시간도 줄였다

오늘 09:59 크래시는 위 셋 중 어느 것도 아니었다 — CMIODALExtensionDevice deviceHasBeenInvalidated, CMIO 내부다. 이것도 프레임워크 안이라 막지는 못한다. 대신 AVCaptureDevice.wasDisconnectedNotification과 AVCaptureSession.runtimeErrorNotification을 감시해 이미 사라진 장치를 참조하는 시간을 줄였다.

→ 두 경로 모두 액터를 건너지 않게 바꿨다. 조명은 LightingStore(NSLock) — 사용자가 움직일 때만 밀어넣고 캡처 스레드는 읽기만 한다. FrameStats는 nonisolated 클래스 — 초당 30번 바뀌는 값은 관찰 대상이 아니다. @Observable로 두면 SwiftUI가 그 횟수만큼 레이아웃을 다시 한다.

→ 결과: 캡처 경로에서 MainActor가 완전히 사라졌다. 24초 실행, 크래시 없음, 매트 OK.

세 번째로 같은 스택을 본 뒤에야

§07의 MTKView.draw 건, ③의 진단 루프, 그리고 이번 건 — 스택 최상단은 매번 SwiftUI였고 수정은 매번 달랐다. 공통점은 하나다. 렌더 경로의 어느 지점이 MainActor를 건드리고 있었다.

개별 호출을 하나씩 옮기는 대신 규칙으로 바꿨다 — 프레임당 실행되는 코드는 메인 액터에 아무것도 올리지 않는다. 값이 필요하면 락으로 보호된 저장소를 읽는다. 이건 §06-3의 "상태를 고치는 것보다 상태를 없애는 쪽이 견고하다"의 동시성 판이다.

07-3맥을 재부팅시킨 누수

이 프로젝트에서 가장 비싼 버그. 앱이 죽은 게 아니라 맥이 재부팅됐다.

사용자 맥북이 재부팅됐다. 앱은 그 전까지 아무 문제도 보고하지 않았다. 남아 있는 것은 커널 패닉 로그 한 줄이었다.

panic(cpu 2): userspace watchdog timeout: no successful checkins from
              WindowServer (1 induced crashes) in 120 seconds

읽는 순서가 중요하다. 커널이 죽은 게 아니다. 화면 합성을 담당하는 WindowServer가 120초 동안 한 번도 체크인하지 못했고, 유저스페이스 watchdog이 그것을 "시스템이 응답 불능"으로 판정해 기계를 내렸다. WindowServer를 굶긴 것은 고갈된 IOSurface였다.

앱은 아무 신호도 주지 않았다

크래시도, 경고도, 느려지는 체감도 없었다. 앱이 정상 동작하는 동안 시스템 자원만 조용히 말라갔고, 먼저 쓰러진 것은 앱이 아니라 화면 합성 서버였다. "앱이 죽으면 알 수 있다"는 전제 자체가 여기서는 성립하지 않는다.

원인 — flush를 한 곳도 부르지 않았다

CVMetalTextureCache는 만들어 준 텍스처를 내부에서 계속 붙잡고 있는다. 놓아주라고 말하지 않으면 놓지 않는다. 그 말이 CVMetalTextureCacheFlush인데, 코드 어디에도 없었다.

// 매 프레임 IOSurface 하나씩 — 30 fps로 45분이면 8만 개다.
CVMetalTextureCacheCreateTextureFromImage(...)
CVMetalTextureCacheFlush(cache, 0)   // ✓ 이 한 줄이 두 곳 다 빠져 있었다

빠진 곳은 CameraCapture와 PersonMatte 둘 다였다. 공통점은 매 프레임 텍스처를 새로 만드는 코드라는 것이다.

원인의 절반은 도구가 아니라 절차였다

이 부분은 정직하게 적는다. 검증이 끝난 뒤 앱을 종료하지 않고 그대로 두는 습관이 반복됐다. 방치된 인스턴스는 화면을 보지 않아도 프레임을 계속 받고, 계속 IOSurface를 쌓는다. 마지막 실행부터 재부팅까지 약 45분 — 30 fps 누적 속도와 시각이 맞는다.

즉 같은 코드라도 "확인하고 바로 종료"였다면 이 사고는 안 났을 가능성이 크다. 버그는 코드에 있었지만 방아쇠는 작업 습관에 있었다. 그래서 수정도 두 방향으로 했다 — 누수를 막는 것과, 누수가 다시 생겨도 시스템까지 끌고 가지 않게 하는 것.

08검증 방법론

"돌아간다"와 "맞다"는 다른 말이다. 이 프로젝트에서 둘을 구분하는 장치들.

원칙: 벤치 수치만으로 판단하지 않는다

추론이 15 ms에 끝났다는 사실은 네트워크가 실제로 실행됐다는 걸 증명하지 않는다. 아무것도 안 하고 15 ms를 쓸 수도 있고, 쓰레기를 계산할 수도 있다. 그래서 모든 벤치에 결정적 입력 → 출력 통계를 붙인다.

깊이 출력: min 0.1748  max 1.0000  mean 0.4352  NaN 0/203056
→ 네트워크 실행 확인 (출력에 변화 있음)

min == max면 상수 — 실행되지 않았다는 뜻이다. NaN이 있으면 수치가 터진 것이다.

독립 경로와 교차검증

가장 강력한 장치다. 같은 입력을 서로 다른 두 구현에 넣고 결과를 비교한다. Core ML은 정규화를 모델 안에 갖고 있고, Metal 4 경로는 내가 셰이더로 직접 한다 — 구현이 독립적이므로 둘이 일치하면 양쪽 다 맞을 확률이 매우 높다.

교차검증 (Metal 4 ML vs Core ML): r = 1.00000
→ 전처리·인덱싱 정확 (두 경로가 같은 깊이를 낸다)

이 한 줄이 이중 정규화 버그를 잡았다. 눈으로만 봤다면 "합성 입력이라 그런가 보다" 하고 넘어갔을 것이다.

레이아웃 불일치를 컴파일 타임으로 끌어오기

Swift 구조체와 Metal 구조체가 어긋나면 런타임에 조용히 쓰레기 값이 들어간다. 컴파일러도, 검증기도 잡아주지 않는다. 그래서 헤더에 크기를 못 박았다.

static_assert(sizeof(SunLight)    == 48,  "Swift 미러와 다르다");
static_assert(sizeof(SunUniforms) == 288, "Swift 미러와 다르다");

그리고 이 가드가 실제로 동작하는지도 확인했다 — 일부러 값을 틀리게 바꿔 빌드가 깨지는 것을 보고 되돌렸다. 검증하지 않은 안전장치는 안전장치가 아니다.

앱보다 CLI에서 먼저

GPU 파이프라인을 SwiftUI 앱 안에서 디버깅하는 건 느리다. 콘솔도 잘 안 보이고, 카메라 권한이 얽히고, 한 번 돌리는 데 빌드+실행이 필요하다. 그래서 Tools/probe_p1.swift가 같은 체인을 합성 입력으로 돌리고 PNG를 떨어뜨린다. 눈으로 볼 수 있는 산출물이 있으면 판단이 빨라진다.

위 예산표는 60 fps 목표의 배분이고, 이것은 현재 앱이 실제로 쓰는 시간이다. flk(플리커 측정)는 --autostart 진단에서만 켜지므로 실사용 경로에는 포함되지 않는다. 30 fps 예산 33.3 ms 안이다.

17.8 → 22.8 ms는 맞바꾼 값이었다 — 구 면광원 · 이중 로브 · 노멀 디테일 텍스처 샘플 2개(§06-6). 하이라이트가 점에서 면적을 가진 빛이 됐고, 그 값을 GPU가 냈다.

그런데 높이장 재구성(§06-8)은 더 느려졌다. 스텝당 투영(나눗셈 2회 + 페치 2회 → 페치 1회)을 없앴는데도 그렇다. 이유는 같은 커밋에서 별도 AO 패스를 지우고 AO를 출력 해상도에서 매 픽셀 계산하게 됐기 때문이다 — half-res 패스였던 것이 2.4 M 픽셀 풀 해상도로 올라갔다. 레이마칭에서 아낀 것을 AO가 도로 먹었다.

회수 계획은 정해져 있다 — AO를 높이장 해상도(518×392)로 내린다(§12). 아직 하지 않았으므로 지금 수치는 "최적화 전"이라고 읽는 것이 맞다.

더 빠르게 만들어야 한다면 — 이 순서로

  1. INT8 / palettized 변형 — 실측 완료, 기각(§07-2). Metal 4 경로에서 실행 불가, Core ML에서도 이득 없음
  2. 입력 해상도 축소 518×392 → 448×336 → 392×294. 깊이는 저해상도에 놀랍게 관대하다. 어차피 업샘플한다
  3. f32 인터페이스를 f16으로 — coremltools 재변환으로 가능한지 확인
  4. 그래도 부족하면 모델 교체(ZipDepth 6.1M) 또는 도메인 증류

학습은 마지막 카드다. 웹캠 앞 상반신이라는 좁은 도메인으로 증류하면 같은 파라미터 수로 훨씬 선명해지지만, 그 전에 위 네 가지를 다 소진해야 한다.

09-1변동폭의 정체

전체 시간만 재면 "변동한다"까지만 알 수 있다. 구간을 쪼개는 순간 답이 나왔다.

깊이 처리 시간이 22~32 ms 사이를 오갔다. 30 fps 예산은 33.3 ms이므로 나쁜 프레임은 경계에 닿는다. 평균이 나쁜 게 아니라 변동폭이 나쁜 종류의 문제다.

첫 가설 — 그럴듯했고, 틀렸다

세그멘테이션이 15 Hz로 Vision을 돌린다. 깊이 추론과 GPU를 나눠 쓰니 세그멘테이션이 도는 프레임만 느려진다고 추정했다. 주기가 있는 부하와 주기가 있어 보이는 변동 — 설명이 맞아떨어졌다.

이 가설을 실험 없이 믿었으면 세그멘테이션 스케줄링을 며칠 만졌을 것이다. 엉뚱한 곳을 최적화하는 데 드는 비용은 아무것도 안 하는 것보다 크다 — 코드는 복잡해지고 원인은 그대로 남는다.

먼저 구간을 쪼갰다

그때까지 계측한 것은 process() 전체 시간 하나뿐이었다. 그 숫자로는 "변동한다"는 사실 외에 아무것도 말할 수 없다. 그래서 네 구간으로 나눠 각각 찍었다 — 인코딩(CPU) · GPU 대기 · affine 정합(CPU) · 플리커 측정(CPU).

구간주체실측 범위판정
enc (인코딩)CPU0.1~0.2 ms안정
gpu (완료 대기)GPU18.6~30.2 ms여기가 전부 변동한다
aff (affine 정합)CPU1.2~1.7 ms안정
flk (플리커 측정)CPU1.1~1.3 ms안정
 1차 구간 실측. CPU 세 구간을 다 더해도 3 ms대이고 흔들리지 않는다. 변동은 전부 GPU 대기 구간에 있었다.

그다음 이등분했다

GPU 대기가 범인이라는 것까지는 나왔다. 그 안에서 세그멘테이션이 원인인지 확인하려면 끄고 켜보면 된다. --no-matte 플래그로 세그멘테이션만 빼고 20초, 켜고 20초를 각각 돌렸다.

 M5, 각 20초, 로그 n=5. 변동폭이 1.8과 1.9로 사실상 같다. 세그멘테이션은 범인이 아니다.

더 흥미로운 것은 양쪽 다 변동폭이 2 ms 미만이라는 사실이다. 22~32 ms라는 큰 변동이 이 조건에서는 재현되지 않았다. 차이는 하나였다 — 이번에는 앱이 이미 한동안 돌고 있었다.

진짜 원인

셰이더·파이프라인 콜드 스타트. 처음 측정이 워밍업 구간을 포함하고 있었을 뿐, 정상 상태의 GPU 시간은 처음부터 안정적이었다. 고칠 코드는 없었다 — 고칠 것은 측정 방법이었다.

그리고 CPU 후처리 2.5 ms를 지웠다

구간 데이터가 있으니 부수적으로 지울 것도 보였다. 둘 다 GPU가 아니라 CPU 쪽이다.

  • affine 정합을 5프레임마다 — 배경 통계는 천천히 변하는데 매 프레임 800샘플을 정렬하고 있었다. 1.3 ms → 0.0~1.0 ms.
  • 플리커 측정은 --autostart에서만 — 이 값은 순수 진단 지표다. 평상시 실행에 들어갈 이유가 없다. 1.2 ms → 0.

최종 실측 — 해상도를 올렸는데 빨라졌다

같은 시기에 출력 해상도를 카메라 네이티브로 바꿨다(§06-2). 픽셀 수가 늘었으니 느려질 것을 각오했는데 결과는 반대였다.

출력 해상도픽셀 수깊이 처리
이전1554×11761.83 M22~32 ms 변동
지금1552×15522.41 M (+31%)17.8 ms 안정
 M5, 캡처 30.0 fps. 지금 값의 원본 로그는 17.85 / 17.80 / 17.99 / 17.86 / 17.76 ms이고 구간은 enc 0.1 · gpu 15.8~16.6 · aff 0.0~1.0 · flk 1.0이다.

이유는 둘이다. 출력이 카메라와 1:1이 되면서 다운샘플 샘플링이 사라졌고 (텍스처 페치가 1:1이다), 위에서 지운 CPU 후처리 2.5 ms가 빠졌다. 픽셀이 31% 늘어난 비용보다 이 둘이 컸다.

이 17.8 ms는 이 시점의 값이다. 이후 스펙큘러를 면광원으로 바꾸면서 23 ms가 됐다(§06-6 · §09) — 구간을 쪼개는 계측이 남아 있었기 때문에 그 5 ms가 어디로 갔는지는 바로 말할 수 있었다.

남는 것

얻은 것은 5 ms가 아니라 측정 방식이다. 전체 시간 하나만 보고 있었을 때는 그럴듯한 가설을 반증할 방법이 없었다. 구간을 쪼개니 CPU가 무죄라는 것이 즉시 나왔고, 이등분하니 첫 가설이 즉시 기각됐다. 가설을 세우기 전에 계측을 쪼개는 것이 순서다.

렌더링한 프레임을 남의 앱 안에 넣는 일은 그래픽 문제가 아니라 행정 문제다. 그래서 행정 비용이 0인 경로를 먼저 뚫었다.

Zoom 진입 경로는 처음부터 셋으로 쪼개 두고 있었다. 이번에 실행한 것은 그중 둘째다.

프레임워크가 아니라 소스로 — 그리고 그 대가

Syphon을 프레임워크로 임베드하지 않고 소스 32개 파일을 앱 타깃에 직접 넣었다 (BSD 라이선스, License.txt 동봉). Metal 서버 경로만 의존성을 따라가며 추렸다 — OpenGL 경로는 제외했다. 이유는 이 프로젝트의 구조다. 프레임워크 임베드는 pbxproj에 링크·임베드·서명 단계를 새로 추가해야 하는데, 동기화 폴더(PBXFileSystemSynchronizedRootGroup)를 쓰는 이 프로젝트에서는 소스를 폴더에 넣기만 하면 자동으로 타깃에 들어간다. 빌드 설정에 손댄 것은 브리징 헤더 한 줄뿐이다.

대신 대가가 있다. 프레임워크가 자동으로 주던 것이 전부 사라진다. 뒤이어 나온 에러 셋은 증상이 제각각이지만 뿌리가 하나다.

use of undeclared identifier 'SYPHONLOG'

prefix header는 따라오지 않는다

SYPHONLOG는 Syphon_Prefix.pch에 있던 매크로다. prefix header는 프레임워크 타깃의 빌드 설정이지 소스의 일부가 아니다. 소스만 복사하면 .pch는 적용되지 않는다.

→ SyphonPrivate.h에 매크로를 정의해 넣었다.

unknown type name 'NSString' · unknown type name 'NSRunningApplication' · use of undeclared identifier 'kCVPixelFormatType_32BGRA'

umbrella header가 해주던 import가 없다

프레임워크로 쓰면 umbrella header가 Foundation · Metal · AppKit · CoreVideo를 알아서 끌어온다. 소스를 직접 넣으면 각 파일은 자기가 필요한 것을 스스로 밝혀야 한다.

→ 각 파일에 필요한 프레임워크를 명시적으로 import했다.

Undefined symbol: _SyphonDispatchSourceCreate

컴파일이 아니라 링크에서야 드러났다

SyphonDispatch.c를 빠뜨리고 헤더만 복사했다. 헤더가 있으니 컴파일은 전부 통과한다. 심볼이 없다는 사실은 링크 단계에서야 나온다.

→ 빠진 .c를 넣었다. 소스 포함에서 파일 목록의 누락은 컴파일러가 아니라 링커가 잡는다.

같이 한 일은 import 스타일 일괄 치환이다. 프레임워크 스타일 경로는 프레임워크가 없으면 성립하지 않는다.

// ✗ 프레임워크 스타일 — 임베드했을 때만 성립한다
#import <Syphon/SyphonServerBase.h>
// ✓ 소스로 포함했으므로
#import "SyphonServerBase.h"
뿌리는 하나다

매크로 미정의, 타입 미정의, 링커 미해결 — 셋은 서로 다른 버그처럼 보이지만 전부 "프레임워크가 자동으로 주던 것이 사라졌다"는 한 문장으로 설명된다. 소스 포함을 택하는 순간 prefix header · umbrella import · 파일 목록을 우리가 직접 다시 만들어야 한다는 뜻이었다. 이걸 처음에 알았다면 세 에러를 한 번에 처리했을 것이다.

검증 — OBS를 설치하지 않고 확인한다

Syphon 서버는 분산 알림으로 자기 존재를 광고한다. 그래서 Tools/syphon_probe.m을 만들었다 — 서버 디렉토리를 조회하는 외부 프로세스다. 앱을 --broadcast로 띄우고 프로브를 돌렸다.

$ ./Tools/syphon_probe
서버: Delight (Delight)
앱 안에서 로그를 찍는 것은 증명이 아니다

"서버를 만들었다"는 우리 앱의 로그는 우리 앱만의 주장이다. Syphon이 성립하려면 다른 프로세스가 그 서버를 볼 수 있어야 한다 — OBS도 그 다른 프로세스 중 하나일 뿐이다. 그래서 검증 도구를 앱 밖에 두었다. 프로브에서 보이면 OBS에서도 보인다.

여기서 시간을 쓴 지점이 하나 있다. 알림 이름은 상수명이 아니라 실제 문자열이다. SyphonServerAnnounce는 SyphonPrivate.h의 #define이고, 실제 값은 따로 있다. 처음에 상수명을 그대로 문자열로 넘겨 "등록된 서버 없음"을 받았다.

// ✗ 상수의 이름을 문자열로 쓴다 — 알림이 영원히 오지 않는다
addObserver:... name:@"SyphonServerAnnounce"
// ✓ #define의 값이 실제 알림 이름이다
addObserver:... name:@"info.v002.Syphon.ServerAnnounce"

앱 쪽 로그는 [Delight] Syphon 서버 시작됨: Delight이고 상태 라인에 송출=ON이 뜬다. 툴바에 송출 토글을 뒀다.

거울상은 송출에 적용하지 않는다

프리뷰는 좌우 반전이다 — 사용자가 거울에 익숙하기 때문이다(§06-1). 그런데 상대방이 보는 영상은 비반전이 정석이다. 반전은 어디까지나 프리뷰 전용이다.

이 구분이 FrameSink 경계에서 자연히 지켜진다. 미러는 composite_split 커널, 즉 프리뷰 경로 안에만 있고, SyphonSink.submit은 원본 텍스처를 그대로 넘긴다. 송출 쪽에서 뒤집지 않기로 결정한 것이 아니라, 뒤집는 코드가 애초에 그 경로에 없다. 싱크 추상화가 정책을 대신 강제하는 셈이다.

OBS 연결 — 순서가 중요하다

  1. OBS에서 소스 추가 → Syphon Client → 서버 목록에서 "Delight" 선택
  2. OBS 가상 카메라 시작
  3. Zoom을 마지막에 실행 — Zoom은 시작할 때 한 번만 장치를 스캔한다. 먼저 켜 두면 가상 카메라가 목록에 없다.

3번 때문에 이 순서를 설정 화면에 그대로 적어뒀다. 모르면 "송출이 안 된다"로 오진하기 딱 좋은 지점이다.

정직하게 — 미해결로 남긴 간헐 크래시

송출을 검증하는 동안 VFX 프레임워크의 NSBundle URLForResource → CFBundleCreate에서 EXC_BAD_ACCESS가 1회 났다. 새로 붙인 것이 Syphon뿐이니 의심은 자연스럽다. 그래서 추측하지 않고 §07-1과 같은 방법으로 조건을 갈랐다.

조건실행크래시
송출 OFF14초0
송출 ON14초0
송출 ON + 매트 OFF14초0
 세 조건 모두 재현되지 않았다 — Syphon은 원인이 아니다.

앞서 기록한 Espresso/Vision 모델 로드 계열의 간헐 레이스와 같은 부류로 보인다(§07-1). 재현 조건을 못 잡았으므로 고쳤다고 쓰지 않는다. 미해결로 남긴다.

09-3OBS 없이 Zoom으로

Syphon은 남이 치른 행정 비용을 빌려 쓰는 길이었다(§09-2). 이번엔 우리 이름으로 Zoom의 카메라 목록에 오르는 길 — 빌드와 임베드까지 갔고, 설치는 조건부다.

목적은 하나다. OBS 없이 Zoom에 직접 나타난다. DelightCamera 타깃을 새로 만들고 CMIOExtensionProviderSource · DeviceSource · StreamSource와 안내 화면 페인터를 넣었다.

설계 판단 둘 — 둘 다 사용자가 겪을 순간에 대한 것이다

  • 고정 UUID를 쓴다(장치 6B9D4F2A-…, 스트림 A1C8E3D7-…). 실행할 때마다 새로 만들면 Zoom이 다른 장치로 인식해, 사용자는 매번 카메라를 다시 골라야 한다.
  • 검은 화면 대신 안내 패턴을 내보낸다. 앱이 아직 연결되기 전이라도 "Delight / 앱을 실행하고 송출을 켜세요"와 텅스텐 색 맥동을 그린다. 검은 화면을 본 사용자는 고장으로 판단한다 — 대기 상태와 고장은 구분되어야 한다.

앱 쪽에서는 OSSystemExtensionManager로 설치를 요청하고, 설정 화면에 요건을 표시한다.

확장은 앱과 다른 환경이다 — 컴파일 에러가 그걸 알려줬다

같은 리포, 같은 Swift, 같은 기계다. 그런데 확장은 앱이 링크하는 프레임워크를 링크하지 않는다. 이 사실이 에러 두 개로 먼저 나타났다.

type 'NSAttributedString.Key' has no member 'font'

.font·.foregroundColor는 AppKit이 주는 확장이다

NSAttributedString.Key 자체는 Foundation에 있지만 .font와 .foregroundColor는 AppKit이 얹은 확장이다. 카메라 확장은 AppKit을 링크하지 않으므로 존재하지 않는다.

→ CoreText 상수를 직접 쓴다 — kCTFontAttributeName, kCTForegroundColorAttributeName.

cannot find 'kIOAudioDeviceTransportTypeVirtual' in scope

CoreAudio 상수도 따라오지 않는다

가상 장치임을 알리는 transport type 상수는 CoreAudio가 준다. 여기서도 프레임워크가 없으니 이름이 없다.

→ FourCC 'virt'(0x76697274)를 직접 넣는다.

정직하게 — 이 머신에서는 설치할 수 없다

빌드되고, 서명되고, 앱 번들 안에 임베드까지 된다. 그런데 설치는 못 한다. 확인한 사실은 둘이다.

$ csrutil status
System Integrity Protection status: enabled

$ security find-identity -v -p codesigning

설치하려면 둘 중 하나가 필요하다. (a) Developer ID 서명 + 공증 + /Applications에 설치, 또는 (b) SIP를 끄고 systemextensionsctl developer on. 둘 다 사용자가 결정하고 실행할 일이지 코드가 우회할 수 있는 것이 아니다.

그래서 코드가 요건을 미리 검사해 설정 화면에 표시한다. 설치가 실패한 뒤 로그를 뒤지는 것보다, 왜 안 되는지 먼저 아는 편이 낫다.

그래서 두 경로가 공존한다

§09-2의 Syphon → OBS 경로는 이 조건 없이 지금 동작한다. 서명 등급도, SIP 상태도, 재부팅도 묻지 않는다. CMIO는 조건이 갖춰진 환경에서 OBS를 지우는 경로이고, Syphon은 그 조건이 없을 때의 경로다. 한쪽이 다른 쪽을 대체하는 것이 아니라, 사용자 환경이 어느 쪽인지가 선택을 정한다.

11회고: 반복된 실수와 반복된 성공

위 문서는 시간순이다. 여기서는 같은 실수와 같은 판단이 몇 번씩 되풀이된 축으로 다시 묶는다. 전부 앞 섹션에 사례가 있다.

1. 추측하지 말고 측정하라 — 그럴듯한 설명은 증거가 아니다

이 프로젝트에서 가장 비싼 실수는 버그가 아니라 검증하지 않은 가설이었다.

  • 변동폭 22~32 ms(§09-1) — 주기적으로 도는 세그멘테이션(15 Hz) 탓이라고 추정했다. 주기가 있는 부하와 주기가 있어 보이는 변동, 설명이 딱 맞아떨어졌다. 구간을 넷으로 쪼개니 변동은 전부 GPU 대기에 있었고, --no-matte로 이등분하니 세그멘테이션 ON/OFF의 변동폭이 1.9와 1.8로 같았다. 진짜 원인은 콜드 스타트였다 — 고칠 코드가 아니라 고칠 측정 방법이었다.
  • 양자화(§07-2) — INT8이면 빨라질 것이라 기대했다. 실측은 Metal 4 경로에서 실행 불가(GPU 타임아웃), Core ML ANE에서 20.31 ms로 F16과 동일. 얻은 것은 파일 크기 절반뿐이라 기각했다.
  • .private → .shared(§06-1) — 성능 저하를 각오한 변경이었는데 통합 메모리라 15.1~15.6 ms로 차이가 없었다. 겁먹고 안 했으면 핀치 z를 못 얻었다.
  • 해상도를 31% 올렸는데 빨라졌다(§06-2 · §09-1) — 1:1 페치로 리샘플이 사라지고 CPU 후처리 2.5 ms가 빠진 효과가 픽셀 증가보다 컸다.

공통 교훈은 순서에 있다. 가설을 세우기 전에 계측을 쪼갠다. 전체 시간 하나만 보고 있으면 그럴듯한 가설을 반증할 방법이 없고, 엉뚱한 곳을 최적화하는 비용은 아무것도 안 하는 것보다 크다 — 코드는 복잡해지고 원인은 그대로 남는다.

2. 보이지 않는 것을 추측하면 버그가 된다 — 세 번 같은 실수

증상은 세 번 다 같은 문장이었다. "핀치한 손을 오브젝트 뒤로 옮기면 광원이 오브젝트 앞에 붙어 고정된다." 원인은 세 번 다 없는 정보를 만들어낸 코드였다.

손 크기로 z를 외삽손 크기는 거리만의 함수가 아니다 — 돌리거나 쥐면 같은 거리에서도 변한다§06-3 도입 → §06-5 제거

지금 규칙은 하나다. 모르면 모른다고 하고 움직이지 않는다. 이웃 깊이의 퍼짐이 크면 가림 경계로 보고 광원을 두고, 손바닥 관절들과 핀치 깊이가 어긋나면 가림으로 보고 광원을 둔다. 추측은 항상 "대부분의 경우 맞다"로 정당화되지만, 사용자가 기억하는 것은 틀린 순간이다.

3. 상태를 고치는 것보다 상태를 없애는 쪽이 견고하다

추정을 개선하는 방향은 "얼마나 좋아졌나"가 항상 확률적이다. 상태를 제거하는 방향은 증상이 발생할 수 없다는 것을 코드에서 읽을 수 있다. 같은 판단을 네 번 했다.

  • 광원 수명(§06-3) — 핀치를 놓으면 광원이 사라진다. "잘못된 자리에 남은 광원"이라는 상태 자체가 없어진다. 단, 이 항목은 이후 뒤집혔다(§06-8) — 상태를 없애는 것이 견고하긴 했지만 조명을 놓을 때마다 어두워져 위치 조정 자체가 안 됐다. 지금은 광원을 남기고, 대신 그 상태가 나쁜 값을 갖지 못하게 막는다. 원칙이 틀렸다기보다 사용감이 원칙보다 위에 있는 경우가 있다.
  • 스냅 애니메이션 제거(§06-5) — 보간하는 동안 광원이 손과 다른 곳에 있는 프레임이 사라진다.
  • UI 노브 제거(§06-7) — 노브가 없으면 잘못 맞춰진 노브도 없다.
  • 캡처 경로에서 MainActor 제거(§07-1) — 액터 경쟁을 조율하는 대신 경쟁 자체를 없앴다.

4. 단위를 바꾸면 그에 딸린 상수가 전부 바뀐다

높이를 미터에서 [0,1] 정규화로 옮긴 것은 커널 한 줄이었다. 비싼 것은 그 뒤였다 — 미터를 전제로 튜닝해 둔 상수들이 코드 곳곳에 흩어져 있었고, 셋 다 컴파일도 실행도 되면서 화면만 죽였다(§06-8).

  • thickness·AO 반경 → AO 전 픽셀 포화 → 검은 화면
  • 감쇠식 계수 1/(1+6d+12d²) → 거리가 uv가 되자 기여 0 → 또 검은 화면
  • 수치 여유가 좁아지며 shadowBias 부재가 표면화 → 평평한 배경에 자기그림자

교훈은 "조심하자"가 아니다. 단위를 바꿀 때는 그 단위가 등장하는 상수를 먼저 전부 세어 본다. 그리고 증상이 "전부 검다"처럼 뭉뚱그려질 때는 항을 하나씩 따로 출력해 본다 — --debug 1~4로 높이장·노멀·AO가 정상임을 확인한 순간 남은 것은 조명 항 하나뿐이었다. §09-1의 이등분과 같은 논리이고, 도구만 시각화였다.

5. 읽으면서 쓰지 마라 — 화면에 스레드그룹이 보이면 그 얘기다

세그멘테이션이 꺼져 있을 때 바인딩할 텍스처가 없어서 heightTexture를 폴백으로 꽂았는데, 그 커널의 출력도 같은 텍스처였다(§06-8). 결과는 정확히 16×16 배수의 블록 아티팩트였다.

여기서 배운 것은 진단 규칙이다. 아티팩트의 크기가 컴퓨트 타일 크기와 일치하면 원인은 셰이더 수식이 아니라 디스패치 단위의 경쟁이다. "바인딩할 게 없으니 아무거나"는 §07의 RAW 해저드와 같은 부류의 실수 — 컴파일러가 잡아주지 않는 계약을 편의로 어긴 것이다.

6. 방치된 프로세스가 시스템을 죽인다

가장 비싼 사고는 맥이 재부팅된 것이었고(§07-3), 앱은 그 전까지 아무 신호도 주지 않았다. 코드의 버그는 CVMetalTextureCacheFlush 누락이었지만, 방아쇠는 검증이 끝난 앱을 종료하지 않고 두는 습관이었다. 보이지 않는 창 뒤에서 30 fps로 45분이면 IOSurface 8만 개다.

그래서 고친 것도 둘이다 — 누수를 막는 한 줄과, 누수가 다시 생겨도 시스템까지 끌고 가지 않는 장치 (10초 주기 메모리 감시, 4 GB에서 스스로 캡처 중단). 후자는 버그 수정이 아니라 실패 반경을 줄이는 코드다. 앱이 자기 자신만 죽일 수 있게 만드는 것이 이 프로젝트에서 새로 생긴 요구사항이다.

7. 검증 도구도 검증해야 한다

이 프로젝트에서 도구가 거짓말한 횟수가 파이프라인이 틀린 횟수만큼 많았다.

  • 교차검증 코드가 틀렸다(§07) — Core ML 출력 Grayscale16Half를 Float로 읽어 r = −0.28이 나왔다. 파이프라인은 이미 맞은 상태였다.
  • 진단 루프가 크래시를 만들었다(§07-1) — 관측하려고 켠 것이 관측 대상을 바꿨다. 관측 코드는 관측만 해야 한다.
  • 알림 이름은 상수명이 아니라 문자열(§09-2) — 상수의 이름을 문자열로 쓰면 알림이 영원히 오지 않는다. 조용히 실패하는 종류다.
  • 안전장치를 일부러 깨봤다(§08) — static_assert 값을 틀리게 바꿔 빌드가 실제로 깨지는지 확인하고 되돌렸다. 검증하지 않은 안전장치는 안전장치가 아니다.

8. 경계를 넘으면 자동으로 주던 것이 사라진다

같은 언어, 같은 리포, 같은 기계인데 실행 환경이 다르면 있던 것이 없다. 세 번 다 컴파일 에러로 먼저 나타났고, 세 번 다 "왜 이게 없지"에서 시작했다.

  • 프레임워크 → 소스 포함(§09-2) — prefix header는 프레임워크 타깃의 빌드 설정이지 소스의 일부가 아니고, umbrella header가 해주던 import도 따라오지 않는다.
  • 앱 → 시스템 확장(§09-3) — NSAttributedString.Key.font는 AppKit이 얹은 확장이고, kIOAudioDeviceTransportTypeVirtual은 CoreAudio가 준다. 확장은 둘 다 링크하지 않는다.
  • 프래그먼트 → 컴퓨트(§06-6) — dfdx/dfdy는 쿼드 래스터화에서 나오는 값이라 커널에 없다.

9. 컴파일러가 안 잡아주는 계약이 가장 오래 걸린다

타입 시스템 밖에 있는 약속들은 런타임에 조용히 틀린다. 그래서 각각에 장치를 하나씩 붙였다.

계약어긋나면붙인 장치
액터 격리 가정(assumeIsolated)참조카운트 경쟁 → 해제된 객체(§07)렌더 경로를 완전한 nonisolated로. 프레임당 코드는 메인 액터에 아무것도 올리지 않는다

10. 잘한 판단들도 기록해 둔다

회고가 실패 목록만 되면 다음에 무엇을 또 해야 하는지를 잃는다.

  • 추론을 GPU 타임라인에 올린 것(§03) — 추론 출력이 GPU 메모리를 떠나지 않는다. 이 구조 하나가 CPU 왕복을 전부 없앴다.
  • 깊이는 저해상도, 조명은 고해상도(§06-2) — 깊이맵은 저주파라 518×392로 충분하다. 이 분리가 "흐릿함"을 없애면서 예산도 지켰다.
  • Syphon을 먼저 뚫은 것(§09-2) — Zoom 진입은 그래픽 문제가 아니라 행정 문제였고, 행정 비용이 0인 경로를 먼저 열었다. CMIO 확장이 SIP·서명 조건에 막힌 지금(§09-3)도 송출은 동작한다.
  • 눈으로 볼 수 있는 산출물을 만든 것(§06-2 · §08) — PNG 덤프 진단 경로가 흰 후광이 실루엣을 정확히 따라간다는 것을 한눈에 보여줬다. 실시간 화면만 봤다면 못 잡았다.
  • 이등분(§07-1 · §09-1) — --no-matte 하나로 크래시 방아쇠를 확정했고, 같은 플래그로 성능 가설을 기각했다. 쓸모를 다한 뒤에도 이등분 도구로 남겨뒀다.
한 문장으로

이 프로젝트가 반복해서 가르친 것은 같은 문장의 두 얼굴이다 — 모르는 것을 아는 척하면(추측한 z, 검증 안 한 가설, 검증 안 한 도구) 반드시 되돌아온다. 그리고 그 반대편에 모른다는 것을 코드가 표현할 수 있게 만드는 일 (신뢰 못 할 깊이는 안 쓴다, 놓으면 사라진다, 노브는 없앤다)이 있다.

12다음 단계

순서에는 이유가 있다. 학습이 필요 없는 것부터 소진하고, 학습은 그것으로 안 되는 지점에만 쓴다.

학습 없이 되는 것 — 여기부터다

항목효과근거
AO를 높이장 해상도로 이동~6 ms 회수지금 가장 큰 낭비다. 재구성(§06-8)에서 AO가 출력 해상도 2.4 M 픽셀로 올라갔다. 깊이는 저주파라 518×392로 충분하다는 것은 이미 §06-2에서 확인했다
레이마칭 계층화 (coarse → fine)같은 품질에 스텝 절반POM의 표준 기법. 거친 스텝으로 교차 구간을 찾고 그 안에서만 세밀하게 본다
높이장 joint bilateral 업샘플실루엣 선명 → 그림자 누출 감소깊이에 이미 쓰는 방식(§06-2)을 높이장에도 적용하는 것
 셋 다 모델을 건드리지 않는다. 첫 항목만으로 재구성 이전 수준(§09)에 근접한다.

도메인 파인튜닝이 실제로 이득인 지점

"모델을 더 좋게"는 대개 게으른 답이다. 그래서 어디가 부족한지부터 특정했다. 깊이 모델은 웹캠 근접 얼굴에서 코 · 입술 · 귀의 미세 기복을 뭉갠다. 큰 형태(머리 대 배경)는 잘 맞는데, 조명이 살아나려면 필요한 것은 그 미세 기복 쪽이다.

지금 쓰는 우회는 원리적으로 순환이다

부족한 디테일을 루마 고주파로 흉내 내고 있다(§06-6 ④). 그런데 루마에는 이미 만들어진 음영이 들어 있다. 조명이 만든 그늘을 다시 지오메트리로 읽어 조명에 쓰는 셈이라, 원본 조명이 강할수록 틀린 방향으로 강해진다. 튜닝으로 완화는 되지만 한계가 원리에 있다.

여기서만 학습이 값을 한다. 레시피는 GT가 필요 없다 — Depth Pro를 교사로 웹캠 도메인 pseudo-label을 만들고 DAv2-small 448²로 증류한다. 추론 비용은 지금과 같고(같은 아키텍처·같은 입력), 도메인이 "웹캠 앞 상반신"으로 좁으므로 더 큰 모델을 가져오는 것보다 대개 이득이다(§07-2).

시간 일관성 — 필요해지면

프레임 간 떨림은 지금 후처리 필터로 8배 줄여 놓았다(§06-4). 그것으로 부족해지면 같은 형태의 답이 있다 — Video Depth Anything을 교사로 시간일관 pseudo-label을 만들어 증류한다. 교사만 무거울 뿐 학생은 그대로이므로 추론 비용은 변하지 않는다.

순서를 지키는 이유

위 세 덩어리는 비용이 완전히 다르다. AO 해상도는 한 줄 수준이고, 증류는 데이터 수집부터다. §09에 적은 원칙과 같다 — 학습은 마지막 카드다. 그 전에 소진할 것이 남아 있으면, 학습은 문제를 해결하는 게 아니라 가린다.
